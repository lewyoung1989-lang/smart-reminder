# 药箱库存批次滑动删除设计

## 目标

在家庭药箱的库存批次列表中支持向左滑动删除。每次删除必须经过二次确认，只删除当前行对应的库存批次，不删除同名药品的其他批次，也不删除药品主记录。

## 交互设计

每个库存批次行使用 Flutter 原生 `Dismissible`，仅允许从右向左滑动。滑动时行后方显示红色背景、垃圾桶图标和“删除”文字。滑动达到阈值后弹出确认对话框：

- 标题：`删除这批药品？`
- 内容：显示药品名称；有批号时同时显示批号，并说明该操作只删除当前批次。
- 次要按钮：`取消`
- 危险操作按钮：`删除`

用户取消或关闭对话框时，列表行恢复原位，不发送网络请求。用户确认后才调用删除接口；接口成功后移除当前行。删除最后一行后显示现有空药箱状态。

## 后端接口

新增：

```text
DELETE /api/v1/inventory-batches/{batch_id}
```

接口要求登录，并通过 `medicine__owner=request.user` 限定可访问对象：

- 删除自己的库存批次返回 `204 No Content`。
- 批次不存在或属于其他用户时统一返回 `404 Not Found`，不泄露其他用户是否拥有该记录。
- 不级联删除 `MedicineItem`，同名药品的其他批次保持不变。

服务端只记录批次内部 ID、结果和异常类型，不记录药品名称、批号或其他用户内容。

## Flutter 数据层

`MedicineCabinetApi` 新增 `deleteBatch(String batchId)`：

- 使用现有 API 基础地址和 Bearer Token。
- 对 batch ID 做路径段编码后请求 `/api/v1/inventory-batches/{id}`。
- 仅把 `204` 视为成功；其他状态码抛出已有的 `MedicineCabinetApiException`。

应用入口把 `_medicineCabinetApi.deleteBatch` 注入 `MedicineCabinetScreen`，界面不直接持有 HTTP 客户端。

## Flutter 状态处理

`MedicineCabinetScreen` 增加必需的 `deleteBatch` 回调。`Dismissible` 使用库存批次 ID 作为稳定 key，避免搜索、分页或删除后复用错误状态。

删除流程由 `confirmDismiss` 控制：

1. 显示确认对话框。
2. 取消时返回 `false`。
3. 确认后调用删除回调。
4. 成功时 `confirmDismiss` 返回 `true`，由 `onDismissed` 立即把批次 ID 加入已删除集合，并从当前 `_batches` 中移除，满足 `Dismissible` 对列表同步更新的要求。
5. 失败时保留当前行，显示 `删除失败，请稍后重试`，并返回 `false`。

删除期间当前行由 `Dismissible` 保持在待决状态，不能重复触发删除。分页请求若在删除期间返回，合并结果时排除已经成功删除的批次 ID，避免刚删除的行被旧分页响应重新加入。页面维护本次页面生命周期内的 `_deletedBatchIds` 集合；重新执行首屏加载或搜索时清空该集合，以服务器最新状态为准。

## 错误与边界

- 网络失败、`401`、`404`、`5xx`：保留列表行并显示统一失败提示。
- 对话框显示期间页面销毁：不再更新状态或显示提示。
- 删除当前搜索结果中的最后一行：显示“没有找到匹配药品”。
- 删除普通药箱中的最后一行：显示“药箱里还没有药品”。
- 同一药品存在多个批次：只移除被滑动行对应的批次。
- 已成功删除后旧分页响应到达：不得重新插入该批次。

## 测试方案

后端测试覆盖：

- 未登录不能删除。
- 用户可以删除自己的单个批次并得到 `204`。
- 同一药品的其他批次和药品主记录保留。
- 删除其他用户批次返回 `404`，数据保持不变。

Flutter API 测试覆盖 DELETE 方法、编码后的批次路径、Authorization 请求头、`204` 成功和错误状态异常。

Flutter Widget 测试覆盖：

- 只能向左滑动，并显示删除背景。
- 滑动后出现二次确认。
- 取消不调用删除回调且行恢复。
- 确认成功只删除当前行。
- 确认失败保留当前行并显示失败提示。
- 删除最后一行切换到正确空状态。
- 已删除批次不会被稍后到达的旧分页响应重新加入。
