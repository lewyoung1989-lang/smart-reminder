# 提醒列表、取消与相机崩溃修复设计

## 目标

本阶段让用户在 App 中查看已经确认创建的提醒，并按“待提醒”“已过期”“已取消”三个状态浏览。用户可以取消尚未到时间的提醒，服务端状态和 iPhone 本地通知保持一致。同时修复拍照录入因缺少 iOS 相机用途声明而被系统强制终止的问题。

## 范围

本阶段包含：

- 当前用户的提醒列表、状态筛选、刷新和游标分页。
- 创建提醒后返回列表并刷新“待提醒”。
- 待提醒的取消确认、服务端禁用和本地通知撤销。
- 相机用途声明，以及拒绝授权或相机调用失败时的页面错误提示。
- 现有提醒数据的兼容迁移、自动化测试、腾讯云部署和 iPhone Release 验收。

本阶段不包含重复提醒、提醒编辑、永久删除、完成打卡、家庭共享、服务端推送、天气任务执行和 AlarmKit 强闹钟。这些能力可以在稳定的提醒列表与执行记录基础上继续扩展。

## 状态语义

`ReminderRule` 增加两个字段：

- `scheduled_at`：带时区的实际提醒时间，建立数据库索引。
- `cancelled_at`：用户取消时间，可为空。

现有 `enabled` 字段继续作为是否启用的持久状态。API 在请求时根据同一个服务端 `now` 计算状态：

- `pending`：`enabled=True`、`cancelled_at IS NULL`、`scheduled_at > now`。
- `expired`：`enabled=True`、`cancelled_at IS NULL`、`scheduled_at <= now`。
- `cancelled`：`enabled=False` 且 `cancelled_at IS NOT NULL`。

时间经过后不需要后台任务修改数据库；下次刷新列表时，提醒自然从待提醒进入已过期。取消不会删除记录，因此用户仍能追溯已取消内容。

数据迁移从现有 `schedule_json.local_datetime` 读取时间。带偏移量的时间直接解析；历史数据若为无时区时间，则使用规则自身的 `timezone`（当前为 `Asia/Shanghai`）解释后保存。无法解析的异常历史记录会使迁移明确失败，避免静默产生错误提醒时间。

## 服务端 API

### 查询提醒

新增：

```text
GET /api/v1/reminders?status=pending|expired|cancelled
```

请求必须携带 Bearer Token，只返回 `owner=request.user` 的数据。`status` 默认值为 `pending`，非法值返回 `400`。每页 50 条，使用稳定游标分页：

- 待提醒：`scheduled_at` 升序，最近将发生的提醒在前。
- 已过期：`scheduled_at` 降序，刚过期的提醒在前。
- 已取消：`cancelled_at` 降序，最近取消的提醒在前。
- 每种排序都使用 `id` 作为最终稳定排序键。

响应项目包含：

```json
{
  "id": "reminder-uuid",
  "title": "喝水",
  "timezone": "Asia/Shanghai",
  "scheduled_at": "2026-08-05T15:30:00+08:00",
  "severity": "notification",
  "status": "pending",
  "cancelled_at": null
}
```

### 取消提醒

新增：

```text
POST /api/v1/reminders/{id}/cancel
```

取消操作在事务内锁定当前用户的提醒：

- 待提醒：设置 `enabled=False` 和 `cancelled_at=now`，返回 `200` 与 `status=cancelled`。
- 已取消：幂等返回 `200`，保留第一次取消时间。
- 已过期：返回 `409`、`code=reminder_expired`，不改变记录。
- 不存在或属于其他用户：统一返回 `404`。

确认草稿创建 `ReminderRule` 时同时写入 `scheduled_at`。查询和取消 API 不接受客户端传入用户 ID、状态或时间。

## App 交互

底部导航的“提醒”入口改为提醒首页，而不是直接显示创建表单。

提醒首页结构：

- App Bar 标题“提醒”，右侧使用 `+` 图标进入创建提醒页面。
- 页面顶部使用三个标签页：“待提醒”“已过期”“已取消”。
- 每条提醒展示标题、本地日期时间和提醒级别。
- 三个列表都有加载、空状态、错误重试、下拉刷新和游标加载状态。
- 状态颜色克制区分：待提醒使用绿色提示，已过期使用中性灰色，已取消使用弱红色。

创建提醒继续沿用现有“输入文字 -> 解析草稿 -> 用户确认”流程。确认成功后：

1. 服务端创建正式提醒。
2. App 安排 iPhone 本地通知。
3. 返回提醒首页，切换到“待提醒”并刷新。

如果服务端创建成功但本地通知安排失败，仍返回列表并明确提示“提醒已创建，但手机通知未安排”。

待提醒行提供取消图标按钮。点击后弹出确认对话框，显示提醒标题和“取消后不会再通知”。确认取消时先调用服务端，再用相同的稳定通知 ID 撤销 iPhone 本地通知，随后将记录移到“已取消”。取消服务端成功但本地撤销失败时，显示“提醒已取消，但手机通知可能仍存在”，不把服务端状态回滚。

## 本地通知接口

`ReminderNotificationScheduler` 增加：

```dart
Future<void> cancel({required String reminderId});
```

`LocalNotificationGateway` 增加按整数 ID 取消通知的方法。安排和取消必须共用同一个 `_stableNotificationId(reminderId)` 映射，确保撤销的是创建时安排的通知。取消不再次请求通知权限。

## 相机崩溃修复

iPhone 崩溃报告显示 `termination.namespace=TCC`，原因是 App 访问相机时缺少 `NSCameraUsageDescription`。`Info.plist` 增加：

```xml
<key>NSCameraUsageDescription</key>
<string>用于拍摄药盒和有效期，识别结果需由你确认后才会加入药箱。</string>
```

`MedicineOcrScreen` 捕获相机调用异常并显示“无法打开相机，请检查相机权限后重试”。用户取消拍照不视为错误。图片仍只上传到私有 MinIO，确认后删除，未确认图片按 24 小时策略清理。

## 错误处理与一致性

- 首屏列表失败显示重试，不清空其他标签已加载的数据。
- 游标加载失败保留当前列表和游标，在底部显示重试。
- 快速切换标签或刷新时使用请求代次隔离，旧响应不得覆盖当前状态。
- 取消按钮在请求期间禁用，避免重复操作；服务端仍保证幂等。
- App 只在服务端取消成功后撤销本地通知，避免网络失败时误删仍有效的通知。
- 所有提醒查询、取消和创建继续使用同一 Bearer 身份隔离。

## 测试与验收

后端测试覆盖：

- 三种状态边界、排序、50 条游标分页和用户隔离。
- 非法状态与匿名访问。
- 取消成功、重复取消、过期冲突和跨用户 404。
- 新提醒写入 `scheduled_at`，历史数据迁移正确解析时区。

Flutter 测试覆盖：

- 提醒 API 请求、状态解析、同源游标和取消错误。
- 三个标签页、加载/空/错误/刷新/分页、快速切换的旧响应隔离。
- 创建成功返回并刷新待提醒。
- 取消确认、服务端调用、本地通知撤销及部分失败提示。
- 相机异常显示错误，iOS `Info.plist` 包含非空相机用途说明。

发布验收：

1. 本地运行全部后端测试、Django 检查、Flutter 测试与静态分析。
2. 构建 iOS Simulator 和签名 Release 版本。
3. 部署腾讯云完整提交 SHA，验证公网提醒列表和取消 API。
4. 在 iPhone 创建一分钟后的提醒，确认它出现在待提醒并收到通知。
5. 创建另一条提醒并取消，确认它进入已取消且通知不再触发。
6. 等待一条提醒时间经过并刷新，确认它进入已过期。
7. 打开拍照录入，确认系统显示相机授权且 App 不再崩溃。
